# Exorus — план разработки

> Поэтапный план по [техническому заданию](SPEC.md). Вся разработка идёт в ветке `develop`, готовые этапы вливаются в `main` через pull request. Выполненные пункты отмечаются по ходу работы.

## Правила работы с репозиторием

| Правило | Решение |
|---|---|
| Ветки | `develop` — рабочая ветка (по умолчанию на GitHub), все коммиты идут в неё. `main` — стабильная, обновляется только слиянием из `develop` |
| Коммиты | Мелкие, атомарные, каждый собирается и проходит тесты. Формат [Conventional Commits](https://www.conventionalcommits.org/) на английском: `feat(core-api): add JWT login` |
| Области (scope) | `core-api`, `ingest`, `ml`, `web`, `desktop`, `infra`, `docs`, `ci` |
| Pull request | `develop` → `main` после завершения этапа, создаётся вручную на GitHub. Слияние через **merge commit** (не squash), чтобы все коммиты этапа остались в истории |
| Теги | После слияния этапа в `main` тег `v0.N.0` |
| CI | GitHub Actions: сборка и тесты на каждый push и PR (появляется на этапе 1) |
| Секреты | Только в `.env` (в `.gitignore`), в репозитории лежит `.env.example` |
| Язык | Код, комментарии, коммиты — английский; документация в `docs/` — русский |

## Структура репозитория

```
exorus/
├─ backend/            Gradle multi-project (Java 21, Spring Boot 3)
│  ├─ common/          общие DTO и схемы событий Kafka
│  ├─ core-api/        авторизация, каталог, плейлисты, комнаты, чат
│  └─ ingest-worker/   импорт Jamendo, Deezer, ffmpeg → HLS
├─ ml/                 Python: FastAPI, эмбеддинги, обучение, оценка
├─ web/                React + TypeScript + Vite (общий код веба и десктопа)
├─ desktop/            Electron-оболочка над web/
├─ infra/              docker-compose, nginx, prometheus, grafana
└─ docs/               SPEC.md, ROADMAP.md, материалы для записки
```

## Этап 0. Подготовка окружения (без кода)

Проверено на ноутбуке: Docker 29, Docker Compose 2.40, Node 24, npm 11, Python 3.11, Java 22.

- [ ] Сделать `develop` веткой по умолчанию в настройках репозитория на GitHub.
- [ ] Получить `client_id` Jamendo на <https://devportal.jamendo.com> (нужен к этапу 3).
- [ ] Java 21: отдельно ставить не обязательно — Gradle toolchain скачает JDK 21 сам.
- [ ] ffmpeg локально не нужен: он будет внутри Docker-образа `ingest-worker`.

## Этап 10. ML: коллаборативная модель, гибрид, оценка

**Тег:** `v0.10.0`

- [ ] `feat(ml)`: загрузка и подготовка публичного датасета, разбиение по времени
- [ ] `feat(ml)`: ALS (базовая) и two-tower (PyTorch)
- [ ] `feat(ml)`: гибрид — объединение кандидатов и ранжирование
- [ ] `feat(ml)`: оценка Precision@K, Recall@K, NDCG@K; сравнение с `/tracks/similar` Jamendo
- [ ] `feat(ml)`: персональные рекомендации, событие `recommendations.updated`
- [ ] `feat(core-api)` + `feat(web)`: главная страница с рекомендациями
- [ ] `docs`: таблицы и графики метрик для записки

**Вопрос, который нужно решить до начала этапа:** треки публичных датасетов (Last.fm, Million Song Dataset) не совпадают с каталогом Jamendo, поэтому обученную на них коллаборативную модель нельзя напрямую применить к своим трекам. Предлагаемое решение: на публичном датасете проводить офлайн-сравнение моделей (метрики для записки), а в самом сервисе обучать коллаборативную часть на собственных событиях из этапа 8 (реальных и тестовых), опираясь на контентную часть при нехватке данных.

**Готово, когда:** есть таблица метрик по всем моделям и рабочая лента рекомендаций.

## Порядок работы над этапом

1. Реализация по пунктам этапа в `develop`: один пункт — один или несколько коммитов, push после каждого.
2. Проверка критерия «Готово, когда» на живом окружении.
3. Отметка пунктов в этом файле.
4. Pull request `develop` → `main`, слияние merge-коммитом, тег.
